# 2026-08-11

## Dynamic key management, stage 1: the `keys` package

First of five stages from `docs/future/dynamic-key-management.md` + its work order (spec converged over five mercurius rounds, work order over six). Stage 1 is the package move with no new capability: `keys/` is created, `APIKeyEntry` splits into a wire form and a domain record, the store and middleware move, and inline config keys start decoding strictly. Reloadable sources, composition, refresh, and staleness all arrive later. Suite green under `-race`.

### Load-bearing decisions (rationale not visible in the diff)

- **`LoadConfig` reads the file into a raw map, strict-binds `api_keys` through `keys.BindConfig`, deletes that key, then binds the rest forgivingly.** The work order specified a forgiving whole-config bind followed by a per-record strict second pass; this is the same guarantee with one mechanism instead of two. The `delete(raw.Fields, "api_keys")` is the load-bearing line — without it the main bind would decode the block a second, weaker way and silently win.

- **`dd.Merge(cfg, raw.Fields)`, not `dd.Bind`.** These differ in more than name: `Merge` runs `ApplyDefaults()` on freshly-allocated nested structs and `Bind` does not. Nothing in this repo implements `dd.Defaulter` today, so the swap had no live effect — but agora's own `AGENTS.md` recommends `ApplyDefaults()` on optional config pointer structs, and we bind `*agora.Config`. The day agora adds one, `Bind` would silently stop honoring it with no failing test. If you are tempted to "simplify" this back to `Bind`, this is why not.

- **Strictness for inline keys is two mechanisms, deliberately.** `dd.Strict()` supplies the refusal to coerce; the `+extra` capture plus `rejectExtras` supplies unknown-field rejection. Strict binding alone would not reject unknown fields on a struct that carries `+extra`, and `+extra` alone gives no coercion protection — which was the gap: the forgiving binder silently rewrites a timestamp-shaped `name` (`2026-01-01T00:00:00Z` binds as `2026-01-01`), changing a key's attribution identity, and a name is the metrics series and later the budget.

- **The strict bind runs whenever an `api_keys` block exists, including `enabled: false`.** Disabling authentication does not make malformed key config valid, and a block that gets switched on later should be found wrong before it is relied on. Recorded in the work order's migration section; it is a user-visible change from previous behavior.

- **`SanitizeDecodeError` is scoped by structural path, not by pipeline stage.** `dd` renders rejected values into its errors and honors `+secret` at neither the intake nor the binding stage, and plaintext `key` is a legal field here, so any error whose path sits beneath `keys[n]` is reduced to that path with the decoder text dropped. Stage 1 has no strict *intake* yet (no `DecodeStrictYAML`), so today only binding errors reach it; the regex fallback becomes load-bearing in stage 2 when file-source intake errors start arriving.

- **`wireFieldName` reconstructs the wire key from the Go field name** (`AllowedModels` → `allowed_models`, `KeySHA256` → `key_sha256`) so a sanitized diagnostic names a field the operator can actually find in their file. It agrees with the explicit `dd` tags today. A future field whose tag name diverges from the snake-cased Go name would silently produce a wrong path again — that is the coupling to watch.

### Gotchas

- `source.go` was renamed `contribution.go` under terminus-canon's `golang-conventions/camelcase-file-naming` — a Go file is named after the single primary type it defines, and that file held only `Contribution`. The work order's package layout groups by concern rather than by primary type, so expect the same correction for `refresh.go` (if `runner` stays its only primary type) and possibly `store.go` (`Store` plus the exported `Snapshot`). The layout is a list of responsibilities; the canon decides filenames. Noted in the work order so stages 2–4 do not pay this four times.

- `expires_at: null` is silently accepted on an inline key while `expires_at: <value>` is correctly rejected as a deferral to the `api-key-expiry` card. The shared null-carve-out helper strips the field before the unknown-field check sees it. Harmless — null means no expiry, which is what config keys do anyway — but the deferral is loud for a value and silent for null.

## Dynamic key management, stage 2: sources, refresh, composition

The large stage. Adds the `Source`/`Watcher` contract, the strict YAML decode pipeline, the file source with fsnotify, the per-source runner, two-pass composition with real precedence, boot-fatal loading with `required: false`, and `SIGHUP` reload with a platform split. Terminus reviewed it in `bc585e876185`. Race suite green.

### Load-bearing decisions (rationale not visible in the diff)

- **During boot, `recompose()` computes the union and returns without publishing.** `finishBoot()` flips `booting` off and recomposes once, and that is the only snapshot boot ever publishes. Two consequences that are easy to misread as bugs: `s.snapshot` is nil until boot finishes (`Lookup` handles it, and nothing serves requests yet), and **digest-collision warnings fire once at the end of boot rather than per install**. Per-install composition would otherwise warn about collisions against a half-assembled union and log a deny-all warning on every healthy startup — a source with no inline keys installs an empty config contribution before its file sources load.

- **`Install` deep-copies outside the store lock, then takes the lock.** The clone is the expensive part and is per-source work; serializing it would put allocation proportional to the key set inside the critical section that composition also needs. Ordering is deliberate, not incidental.

- **`LoadResult.validate()` is `r.unchanged == (r.contribution != nil)`.** It reads oddly and is a compact XOR: the two success arms must disagree. Both set and neither set are equally programming errors — guarding only the empty one leaves the dangerous half open, since dispatch checks `IsUnchanged()` first and a result claiming both would silently discard its records while advancing freshness.

- **`Unchanged` at boot is fatal even for a `required: false` source.** A load *failure* on an optional source is tolerated and logged; a source confirming data it has never loaded is a source bug rather than an availability problem, and an availability opt-out should not mask it. The asymmetry is intentional.

- **`Validate` rejects any `max_staleness > 0` outright**, with a message saying it is unsupported until staleness enforcement exists. Accepting a fail-closed knob that silently does nothing is worse than refusing it. **Stage 3 must lift this guard** and replace it with the real `max_staleness > poll_interval + timeout` rule; if it survives, the feature ships permanently disabled and reads as a validation bug rather than an unfinished stage. Same shape for the flat `Warn` on refresh failure, which becomes level-by-age once age is tracked.

- **`Validate` resolves and writes back the positional source name** (`file[0]`) so the store, the logs, and any later metrics all see one settled identity. It is idempotent, which matters because both `LoadConfig` and `NewStoreFromConfig` call it.

- **`Close()` orders cancel → `wg.Wait()` → close watchers.** Closing the fsnotify watcher before its goroutine exits would be a use-after-close; joining first makes that unreachable. `cleanup()` calls `Store.Close()` before providers, share, accesses, and agora for the same reason one level up — runners can be mid-request against a borrowed transport.

### Gotchas

- **`fileSource.Load` ignores its context deliberately** (a file is read whole or not at all, per the spec), which means a read hung on a network mount blocks `Store.Close()` inside `wg.Wait()` and stalls `SIGTERM`. Accepted, and the only place shutdown can hang.

- The fsnotify watch is on the **containing directory**, never the file, because editors replace by rename and a watch on the inode does not survive it. Events are filtered to the target's base name *or* `..data`, which is the Kubernetes ConfigMap symlink swap. Both are covered by tests that drive a real store.

- Decode-error sanitization now covers strict *intake*, not only binding. Verified empirically that no plaintext reaches an error for a hex (`0xdeadbeef`), octal (`0o755`), or leading-zero (`007`) key value, in both `key` and `key_sha256`, plus the duplicate-key-within-a-record case — which is not in the typed error list and survives only via the regex fallback on the rendered string. That fallback is load-bearing; treat it as such when adding intake paths.

- `NewStore` is now reachable only from tests; production goes through `NewStoreFromConfig`. It stays exported because `gateway/handler_test.go` builds a store from outside the package.

### Live state

- Stage 2 is uncommitted at the time of this entry. `max_staleness` and the metrics instruments do not exist yet; `Reload` config is parsed and validated but has no runtime effect beyond the guard above.

## Dynamic key management, stage 3: staleness and instruments

Age tracking, the escalating refresh warning, the exact-deadline exclusion evaluator, exclusion with contribution retention, and the four OTel instruments. Three terminus rounds, all `clean` (`12b973ff8421`, `cc74a63c3215`, `f4d33e0aaddb`); the middle one raised two non-blocking `constructor-convention` advisories, both applied — `Meters` became unexported `meters`, and `newSystemDeadlineTimer` returns its concrete type with the interface wrapping moved to the call site.

### Load-bearing decisions (rationale not visible in the diff)

- **Exclusion is driven by an armed timer owned by a dedicated goroutine, never by a ticker and never by refresh activity.** A sampling ticker leaves a contribution in service for up to a tick past its deadline, which is the same defect as evaluating on refresh completion at smaller magnitude — `max_staleness` is the fail-closed control, and a bound that is approximately a bound is not one.

- **Transitions publish a versioned deadline and signal; the evaluator owns the timer.** `armDeadlineLocked` runs under `s.mu` at the end of every `recompose` (and from `Touch` when no recompose is needed), writes `deadlineAt`/`deadlineArmed`/`deadlineVersion`, and does a non-blocking send on a cap-1 channel. The evaluator wakes, re-reads current state under the lock, and skips if the version is unchanged. **This shape exists so a transition never resets a timer concurrently with its receiver** — the obvious alternative, resetting a shared `*time.Timer` from whichever goroutine notices, is a race that would be intermittent and unpleasant. The cap-1 signal coalescing is safe precisely because the evaluator reads current state rather than the signal's payload.

- **The staleness test asserts what duration each timer was armed to, not that exclusion eventually happens.** After installing a second source one minute into a ten-minute window, the test requires the timer to re-arm to **9m** — the first source's remaining deadline. A test that calls the evaluator by hand at the deadline passes under a broken implementation, which is exactly why the `deadlineTimer` seam exists alongside the injected clock. If this test is ever "simplified" to drive the evaluator directly, it stops testing the property it was written for.

- **`Validate`'s stage-2 placeholder is gone**, replaced by `max_staleness > poll_interval`. That is the real rule *while the file source is the only source*, because a file source has no timeout. **Stage 4 must extend it to `poll_interval + timeout`** when the HTTP source introduces one; `30s`/`5s`/`31s` would otherwise validate and then flap, since a refresh starting at the poll boundary can still be in flight when the deadline fires. Recorded in the work order's stage 4 section too.

- **The refresh failure log distinguishes three conditions** the work order treated as one: holding last-known-good, holding a contribution that is *already excluded* (where "holding last-known-good" would mislead, since those records are out of the union), and having never loaded at all (where there is nothing to hold). Escalates to `Error` at ten poll intervals of age, `Warn` below.

- **Observable gauges skip non-reloadable and never-loaded sources.** `config` is boot-resident and has no deadline to miss, so a series for it would climb forever and every alert rule would have to filter it by name. A never-loaded source emits nothing rather than an age from the zero time (reads as a broken exporter) or zero (reads as perfectly fresh, the fail-open direction). Absence is the honest third answer and is itself alertable.

### Gotchas

- The metric callback takes `s.mu`, so collection briefly contends with composition. Bounded and fine, but it means a pathologically slow `recompose` would show up as scrape latency rather than as itself.

- `Touch` re-arms without recomposing when the source was not excluded, and recomposes when it was. Both paths must arm — an early return that skipped arming on the common path would silently stop the deadline clock after the first successful confirmation.

### Live state

- Stage 3 is uncommitted at the time of this entry. Remaining: stage 4 (HTTP source) and stage 5 (docs, zrok token redaction, close-out).

## Dynamic key management, stage 4: the HTTP source

The management-plane source now loads `GET {base_url}/v1/keys` through a gateway-injected client, strictly decodes the JSON envelope, and participates in the same boot, refresh, composition, staleness, and cleanup lifecycle as file sources. Conditional requests, the complete-set `count` check, pagination rejection, direct/agora/zrok transport selection, and HTTP-specific config resolution all land here. Stage 3 was committed as `b22b118` before this work began. Race suite, vet, native build, and Windows cross-build are green.

### Load-bearing decisions (rationale not visible in the diff)

- **The `keys` package borrows an `*http.Client` through `HTTPClientFactory` and never constructs or mutates transport state.** Every `Load` derives its timeout with `context.WithTimeout`; setting `http.Client.Timeout` would mutate a client the agora dialer caches by tunnel name and may share with providers. Tests seed and compare all four client fields — transport, redirect policy, jar, and timeout — on both success and timeout paths. The gateway remains the sole owner of direct/agora/zrok selection and appends key-source zrok accesses to its existing cleanup list.

- **The validator belongs to the accepted representation, not merely the response.** A rejected `200` leaves the previous ETag untouched; an accepted ETag-less `200` clears it. The request snapshots the validator it actually sent and accepts `304` only when that request carried `If-None-Match`, so neither first boot nor the poll after an ETag-less response can manufacture freshness from an unsolicited confirmation. A real conditional `304` flows through `Touch` and can reinstate a retained contribution after staleness exclusion.

- **Pagination headers are checked above status dispatch.** `Link` relations `next`, `prev`, `first`, and `last`, plus any `Content-Range`, reject even a `304`. Accepting the status first would let a bodyless response reset freshness before the source's v1 protocol violation was noticed. The Link splitter tracks URI targets and quoted parameters so a comma inside either cannot create a false boundary.

- **HTTP JSON has its own strict envelope intake but shares the wire-record mapping.** `count` remains a pointer so absent and zero differ; null is treated as absent only after the remaining envelope binds, preserving the promised version-before-count diagnostic order. Record null carve-outs and all value-sanitizing decode behavior are the same helpers used by inline and file keys. The response body is capped at 32 MiB before decoding, adopting the work order's explicit addendum against an endpoint that streams until timeout.

- **`max_staleness` now accommodates `poll_interval + timeout`, with overflow rejected.** The stage-3 file-only rule intentionally had no timeout term. Adding it at the source-type boundary prevents a refresh that starts at the poll deadline from being excluded while its permitted request is still in flight.

- **`collectAgoraTunnels` no longer treats a nil provider block as a global early return.** Provider gates remain individually guarded, and enabled HTTP key sources contribute their tunnels independently. The invariant is now that collection mirrors both `initProviders` and `initKeyStore`; a gateway whose only overlay consumer is its key source must still attach that tunnel.

- **Agora wins when an HTTP source configures both overlay mechanisms.** The gateway logs the choice, never constructs the zrok access, and passes the source's base URL through unchanged so TLS still rides the tunnel end to end. Store shutdown runs and joins HTTP refreshes before provider, zrok, or agora owners close their borrowed transports; the lifecycle test holds an in-flight request open to prove the ordering rather than merely checking call sequence.

### Gotchas

- **Zrok access creation still uses the existing `NewAccess(shareToken)` signature in this stage.** Its legacy lifecycle logs print the operator-supplied token. Stage 5 owns the repo-wide redaction change to `NewAccess(label, shareToken)` and the related provider/share call sites, as the work order specifies; Stage 4 only adds the key-source call site and cleanup ownership.

- An optional (`required: false`) HTTP source tolerates a failed boot request and starts with no contribution, but invalid configuration or failure to construct its requested overlay client remains a constructor error. This matches the file source: `required` is an availability choice, not permission to accept a source the gateway cannot build.
