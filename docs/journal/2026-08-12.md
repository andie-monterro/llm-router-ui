# 2026-08-12

## `isNetworkError` and `context.DeadlineExceeded` — supersedes the 2026-07-17 note

A terminus review flagged `isNetworkError` excluding `context.DeadlineExceeded` as a blocking `failover-network-only` violation. Investigated; the code is correct, the canon was incomplete, and the 2026-07-17 journal entry is stale. That entry states `context.DeadlineExceeded` is "deliberately NOT excluded" — the opposite of what the code does today, and a plausible reason this keeps reading as a defect.

**The code excludes both sentinels, deliberately and with test coverage** (`providers/multiLocal_test.go` asserts `context.Canceled` and `context.DeadlineExceeded` are non-network, bare and wrapped in `url.Error`). The change postdates the 2026-07-17 entry.

### why the exclusion is right

There are three error classes on the request path, not two:

- **endpoint failures** — connection refused, DNS, an endpoint-side `i/o timeout`. Travel with the endpoint; the same request succeeds elsewhere. Fail over.
- **application errors** — an HTTP status from a live backend. Travel with the request; replaying multiplies the failure.
- **request-scoped failures** — the caller's context cancelled or its deadline expired. Also travel with the request, and are the class most easily mistaken for the first, because "timeout" names both a dead endpoint and a spent caller clock.

When the caller's deadline is already spent, every retry re-expires the instant it is attempted, so failing over converts one dead request into a sweep that marks the **entire pool** unhealthy — an outcome that outlives the request that caused it. A hung endpoint is still removed from rotation, because `probe` does not route through `isNetworkError` and runs on the health checker's own context.

### the non-obvious part, verified rather than assumed

Agora's `tunnel.Dial` formats an overlay failure as `fmt.Errorf("...: %v: %w", err, ErrTransient)` — the cause is flattened with `%v`, so the original `net.Error` type is destroyed and only a plain sentinel is wrapped. Read alone, that says a dead agora tunnel would classify as non-network and never fail over.

It does not, and the reason is worth knowing before anyone "fixes" this:

```
overlay failure (cause flattened by %v)   bare=false   via http.Client.Do=true    → fails over
caller deadline propagated by agora                    via http.Client.Do=false   → no failover
expired caller ctx, end to end                         isNetworkError=false
```

**`*url.Error` implements `net.Error` itself** (it has `Timeout()` and `Temporary()`), so anything `http.Client.Do` returns satisfies `errors.As(err, &netErr)` no matter what the transport did to the underlying type. The sentinels are the only thing that short-circuits before that check. Zrok is unaffected either way — its dials fail under ziti's own `ConnectTimeout` with ziti errors.

So the classification holds on the direct, agora, and zrok paths alike. Checking only agora's error construction, without following it through `http.Client.Do`, produces the opposite and wrong conclusion.

### disposition

- Code unchanged.
- `failover-network-only` amended in terminus-canon: its statement enumerated "connection refused, timeout, DNS failure" and had names for only two classes, so a reviewer reading "timeout is a network error" correctly flagged the exclusion by the letter while the quality's own `why` ("travels with the endpoint" vs "travels with the request") already resolved it the other way. The amendment names the third class, adds a skip for the sentinels, and adds a flag in the opposite direction so it cannot be read as licence to swallow a genuine endpoint timeout.
- 2026-07-17's line carries a pointer here.

## Two blocking terminus findings, both pre-existing

A later full sweep surfaced two real defects in code the key-management arc never touched. Both are worth recording because both had been latent for a long time and neither had test coverage asserting the wrong behavior — which is why nothing broke when they were fixed.

- **`Local.parseError` read only Ollama's envelope.** It decodes `{"error": "message"}`; a standard OpenAI `{"error": {"message": ..., "type": ...}}` fails that unmarshal and falls to the default branch, becoming `ErrorTypeServer` -> HTTP 500 with the raw body interpolated into the client-visible message. The docs advertise the local provider as working with "Ollama, vLLM, llama-server, SGLang, or any OpenAI-compatible backend" — and the three OpenAI-compatible ones were exactly the ones whose errors were mangled, while Ollama, the odd shape out, was the only one handled. `openai.go` already had the right pattern; local was the only provider not following it.

- **`validateProviders` never validated `base_url`.** A value with no scheme or an unsupported one initialized cleanly and failed at request time. The key subsystem's `Validate` had required an absolute HTTP(S) URL of a source `base_url` since stage 4, so the same class of configuration was loud in one subsystem and silent in the older one.

**The body-embedding fix was scoped to `local` deliberately.** `openai.go` and `anthropic.go` also interpolate an unparsed body into their default branch, and that was left alone: those front known vendor APIs, while local fronts an arbitrary operator-configured backend — possibly reached over an overlay — whose response body could be anything, including a proxy's debug output. Widening it is a separate decision, not a consequence of this one.

A third, smaller finding followed: **OpenAI startup errors named `providers.openai.*`, which is not a key the gateway reads.** The block is `providers.open_ai` — `OpenAI` snake-cases to `open_ai`, which is the one field name in the config tree where that transformation surprises. An operator following the message would search for a key that does not exist. Fixed at all four sites (`expandEnv` ×2, the `validateProviders` `check` call, and the routing-provider error) plus two test expectations.

Worth recording that **the class was checked and is a class of one**: every other config path appearing in a message — `api_endpoint`, `workgroup_ids`, `zrok_share_token`, `max_staleness`, `poll_interval`, `allowed_routes` — already matches its YAML key, because `OpenAI` is the only multiword *type-name* segment that reaches a path string. No need to re-survey this.

The mismatch surfaced only because the `base_url` validation added an hour earlier used the correct spelling, putting both forms in one file.

## `cmd/dummy-keys`, and the first live smoke of the HTTP key source

Implemented the `dummy-keys-reference-server` roadmap card: a standalone binary serving the published `GET /v1/keys` contract from a file, mirroring `cmd/dummy-model` in shape.

**It deliberately does not share the gateway's wire structs.** `keys`' envelope types are unexported to hold the store's ownership seam, and exporting them to feed a demo would spend a real boundary on convenience. The server marshals plain maps, and the binding is a test that stands up a genuine `keys.Store` — through the exported `NewStoreFromConfig` and `HTTPSourceConfig`, exactly as an operator wires it — against the running server. Drift is therefore caught through the bytes, which is what a third-party management plane implements against; shared structs would have agreed even while both sides drifted together.

**The fault injection is the substance, not a nicety.** Six faults each have to be *rejected by the gateway's own decoder* for their test to pass — a fault the gateway accepts is not a fault. That makes the fault list a live check on the count guard, the pagination rejection, the unsolicited-`304` guard, and strict decoding, rather than a demo affordance.

### live smoke — the first end-to-end run of the HTTP source

Ran `dummy-model` (:8081), `dummy-keys` (:8082), and the gateway (:8080) together against a real socket. Everything the arc claimed, observed rather than asserted:

- boot logged `precedence order [config control-plane] with record counts [config=0 control-plane=2]`
- a served key authenticated (200); an unknown key got 401; a served key restricted to `claude-*` got a 403 `permission_error` for `dummy` — authenticated but not authorized, which is the distinction the design draws
- conditional polling worked at the wire: matching `If-None-Match` → 304, stale validator → 200, weak `W/` prefix → 304
- **live revocation**: deleting a record and sending `SIGHUP` turned that key's next request into a 401 with no restart
- **management plane dark**: killing `dummy-keys` left the remaining key authenticating from last-known-good, with the log line carrying the age and the retention state — `refresh failed; last successful load was 5.003195868s ago; holding last-known-good: key API request failed: dial tcp 127.0.0.1:8082: connect: connection refused`. Note it names the transport failure and no token, no body.

That last line is the one worth keeping: it is the staleness story, the sanitization rule, and the escalating-warning shape all visible in a single message from a real process.

**All three were found on a `kind: full` sweep, not a changeset review.** A full sweep against a canon that has grown since the code was written keeps surfacing pre-existing drift, and the useful triage question on each finding is "is this the arc's, or the repo's?" — these were the repo's, and they belong in their own commit rather than folded into whatever branch is in flight. Worth noting too that they appeared only after several rounds of cosmetic `lowercase-output` findings had been cleared; clearing noise seems to let the reviewer reach substantive material.
